# Fish 私有消息系统 — 协议规范 v1

一对一（A↔B）中转消息协议。协议与平台解耦：任何客户端（手机/桌面/agent）按本文档实现即可接入。

## 1. 概览

- 服务端职责：鉴权、消息路由、存储。不含任何业务逻辑。
- 身份：配置文件预置两个固定身份 `a`、`b`，各持一个密钥（token）。无注册。
- 传输：
  - WebSocket `GET /ws`：实时收发、回执、增量同步。
  - HTTP：图片上传/下载、健康检查。
- 编码：UTF-8 JSON 文本帧。

## 2. 鉴权

| 通道 | 方式 |
|---|---|
| WS 握手 | `Authorization: Bearer <token>` 请求头，或 `?token=<token>` 查询参数（浏览器 WebSocket 无法自定义头时使用） |
| HTTP | `Authorization: Bearer <token>` 请求头；文件下载额外支持 `?token=` |

- token 无效 → WS 握手返回 401 / HTTP 返回 401。
- 服务端根据 token 确定身份（`a` 或 `b`），对端即另一方。
- 同一身份允许多个并发连接（手机+电脑同时在线），消息投递给该身份的全部在线连接。

## 3. 帧结构（信封）

```json
{"v":1, "type":"msg.send", "id":"req-1", "ts":1760000000000, "data":{ }}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| v | int | 协议版本，当前 1 |
| type | string | 帧类型，见 §4 |
| id | string | 客户端生成的请求关联 id（响应帧原样回传），服务端主动推送帧无 id |
| ts | int64 | 发送方 Unix 毫秒时间戳 |
| data | object | 各帧类型自定义载荷 |

## 4. 帧类型

### 4.1 客户端 → 服务端

| type | data | 说明 |
|---|---|---|
| `msg.send` | `{kind:"text", body:"..."}` 或 `{kind:"image", file_id:"...", w,h,size}` | 发消息 |
| `msg.ack` | `{seq:123}` | 接收端确认已收到该消息（送达回执） |
| `sync` | `{after:N, limit:100}` | 拉取 `seq > N` 的历史消息，limit ≤ 200 |
| `ping` | `{}` | 心跳 |

### 4.2 服务端 → 客户端

| type | data | 说明 |
|---|---|---|
| `ready` | `{you:"a", peer:"b", peer_online:true, last_seq:100}` | 连接鉴权成功后发送 |
| `msg.ack` | `{ref:"req-1", seq:101, ts:...}` | 服务端已收到并持久化 `msg.send`（ref 为请求帧 id） |
| `msg.new` | `{seq:102, from:"b", kind:"text", body:"...", ts:...}` | 投递消息（含离线补投与实时推送，同构） |
| `msg.delivered` | `{seq:102}` | 对端已通过 `msg.ack` 确认（发送方收到的送达回执） |
| `sync.done` | `{msgs:[msg.new载荷...], has_more:false}` | `sync` 响应，消息按 seq 升序 |
| `presence` | `{peer:"b", online:false}` | 对端在线状态变化推送（服务端在身份首条连接建立/末条连接断开时主动推） |
| `pong` | `{}` | 心跳应答 |
| `error` | `{code:4003, message:"...", ref:"req-1"}` | 错误，ref 可选 |

### 4.3 错误码

| code | 含义 |
|---|---|
| 4001 | 未鉴权（WS 已连接但尚未完成鉴权即发业务帧） |
| 4002 | 鉴权失败（token 无效） |
| 4003 | 参数错误（缺字段/超限） |
| 4004 | 不支持的帧类型或 kind |
| 4005 | 文件不存在 |
| 5000 | 服务端内部错误 |

## 5. seq 语义（核心）

- 服务端为每条消息分配**全会话单调递增 seq**（从 1 开始）。
- 客户端本地记录已收到的最大 seq（游标）：
  - 上线后发 `sync {after: 游标}` 补拉离线消息；
  - 在线期间被动接收 `msg.new`。
- 按 seq 幂等去重：客户端收到 seq ≤ 游标的消息直接丢弃。
- 投递顺序保证：按 seq 升序投递。

> **重要**：`ready.last_seq` 是**服务端**当前最大 seq，不是客户端本地游标。
> 客户端必须用自己记录的本地游标作为 `sync.after`，**不得**用 `last_seq` 覆盖本地游标，
> 否则首次连接（本地游标为 0）或换设备时将丢失全部历史消息。
> `last_seq` 仅用于判断「本地是否落后」以决定是否发起 `sync`。

> **游标作用域**：客户端游标只能与「本地已渲染/已存储的消息」绑定。
> 若客户端只保存游标、不持久化消息内容（如浏览器刷新导致界面清空），
> 游标必须同时归零，重连时从 `after:0` 全量拉取；否则会出现
> 「游标显示已收到 N 条，但界面为空，只能看到新补投消息」的缺陷。
> 需要跨会话保存消息的客户端，应把游标与消息一起持久化（游标不得单独持久化）。

## 6. 消息时序（正常路径）

```
A                                服务端                                B
│ msg.send(id:req-1,text"hi") ──► │                                    │
│                                 │ 持久化, 分配 seq=101               │
│ ◄── msg.ack(ref:req-1,101) ──── │                                    │
│                                 │ ──► msg.new(seq:101,from:a) ──►    │ (B 在线)
│                                 │                          B 处理    │
│                                 │ ◄──────────────── msg.ack(101) ── │
│ ◄── msg.delivered(101) ──────── │                                    │
```

- B 离线时：消息已落库，B 上线后 `sync` 补投；`msg.delivered` 在 B 补投后回执时补发（A 重连后 sync 不含回执，本期回执为尽力而为，不持久化回执状态）。

## 7. 图片消息

1. `POST /api/files` （multipart/form-data，字段名 `file`，Bearer 鉴权）→ 返回 `{"file_id":"...","size":123}`
2. WS 发 `msg.send {kind:"image", file_id, w, h, size}`（w/h 可选）
3. 接收端展示：`GET /api/files/{file_id}?token=xxx`

限制：单文件 ≤ 10MB；类型仅 `image/jpeg|png|gif|webp`。

## 8. 心跳与连接管理

- 客户端每 30s 发 `ping`，服务端立即回 `pong`。
- 服务端 90s 未从连接读到任何帧则主动断开。
- 断线重连由客户端负责：重连 → `ready` → `sync` 补投。

## 9. 容量限制（2C2G 目标）

| 项 | 限制 |
|---|---|
| 文本消息单帧 | ≤ 8 KB |
| 图片单文件 | ≤ 10 MB |
| sync 单次 limit | ≤ 200 |
| 历史保留 | 永久（可用 SQL 手工清理，见部署文档） |

## 10. 版本

- `v=1` 为当前版本。服务端收到不认识的 v → `error 4004`。
